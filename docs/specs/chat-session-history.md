# 聊天会话历史规格

状态：已实现（2026-10-15），落库与滚动摘要同一期上线  
范围：已登录成员的多轮对话，覆盖三件事——**存储**（换浏览器仍能看到会话列表和正文，Redis 被清空或未持久化重启后已完成的对话仍在）、**隔离**（第 7 节）、**上下文压缩**（第 8 节）。

## 0. 实现记录

第 14 节的决定按这样落地：

- 决定 6：落库和摘要同一期上。
- 决定 7：摘要用这一轮回答所用的那个对话模型（本校配置的，或学生自带的密钥），不另接平台模型。平台目前没有单独的便宜模型可配，等有了再换。
- 决定 8：采纳。最近窗口为 `MAX_PROMPT_CHARS`（6000）字符预算，至少 2 轮、至多 `MAX_PROMPT_TURNS`（10）轮。
- 决定 9：采纳。`chat_messages.tables` 存结构化表格，刷新后表格还在。

与正文不同、或正文没写到的地方：

- **摘要按批触发**，不是每轮都推进。保留窗口 `KEEP_TURNS = MAX_PROMPT_TURNS − SUMMARY_BATCH_TURNS`（10 − 5 = 5 轮）。窗口外未摘要的部分攒满 5 轮才调一次模型，一次压 5 轮。这样每 5 轮只多一次模型调用，而不是每轮一次。写回用 `summarizedSeq` 做乐观锁，两个并发的摘要任务只有一个能写进去。
- **失败的回答不落库**。以「出错了」「对话模型未配置」「检索失败」这几类前缀开头的回答，既不写库，也不在回填时补进去。
- **重新回答、编辑重发只作用于最后一轮**。前端在请求里带 `replace_question`。后端先把 Redis 里最后一轮回滚掉（`update_state(..., as_node="finalize")`），再删掉库里最后两条消息，然后按新问题重答。不支持改中间某一轮。
- **别人的或已删除的 `thread_id`**：`GET messages` 和 `POST /api/chat` 都返回 404「这个会话不存在或已经删除，请新建对话」。前端收到后静默开一个新会话，发消息时还会把这句话重新问一遍。
- **访客**：`GET messages` 仍读自己那个访客线程在 Redis 里的内容，不返回 404。会话列表对访客返回空数组。
- **数据库不可用**：列表返回 503。取消息回退到 Redis。聊天照常进行，只是这一轮不落库。
- **前端编号存储**：`localStorage` 的键按用户分开，即 `zhiyue.threadId:{userId}`。旧键 `zhiyue.threadId` 首次读取时迁移过来。嵌入挂件用 `sessionStorage` 的 `zhiyue.embed.threadId`。
- **打开页面时**，本地没有编号就开一个新的空会话，而不是第 10 节说的「打开最近一条」。历史对话在左侧抽屉里，按今天、昨天、7 天内、更早分组。换浏览器登录后先看到欢迎页，比直接落进一段旧对话更不容易让人困惑。
- **库表**：迁移是 `frontend/prisma/migrations/20261015090000_chat_history`。后端 `DATABASE_URL` 未配置时整套历史功能关闭，行为回到 Redis-only。

## 1. 现在的缺口

一次对话有三处状态，没有一处同时满足「能按人列出」和「Redis 丢了正文还在」。

| 数据 | 位置 | 换浏览器 | Redis 清空或未持久化重启 |
| --- | --- | --- | --- |
| 当前会话编号 `tid` | 浏览器 `localStorage` 键 `zhiyue.threadId`，并写入地址栏 | 丢失，新浏览器找不到上次的编号 | 不受影响 |
| 对话正文 | Redis 里的 LangGraph checkpoint，键为 `{学校id}:{用户id}:{tid}` | 还在，但没有列表就点不回去 | 丢失 |
| 登录身份 | 浏览器里的 JWT，有效期 12 小时 | 需重新登录；身份仍是同一个用户 | 不受影响 |

`POST /api/sessions` 只返回一个 UUID，不落库。`GET /api/sessions/{tid}/messages` 只读 Redis 快照。快照里的 `messages` 最多保留 `MAX_STORED_TURNS`（默认 30）轮。发给模型的是其中最近 `MAX_PROMPT_TURNS`（默认 10）轮。

本项目的 `RedisSaver` 没有配置 TTL。记录不会按时间自己过期，但会在 `FLUSH`、未开 AOF/RDB 的重启，或内存淘汰时消失。

长期记忆（「记住：……」）在 Redis 哈希 `memory:{学校}:{用户}`，不在本规格内。

## 2. 调研结论

LangGraph 文档把 checkpointer 定义成**同一次 thread 的短期执行状态**：用 `thread_id` 恢复图的 state。生产示例用的是 `PostgresSaver`。`list(config)` 和 `get_state_history` 都要先知道 `thread_id`，不能按用户查出「这个人有哪些会话」。平台版才另有 thread 管理接口；开源 checkpointer 没有这层目录。

Redis checkpointer 的 TTL 是可选能力，单位是分钟，用来让热线程过期。它解决的是体积，不是「清空后还能读」。

因此常见接法是拆开两层：

1. **产品记录**放在主库。会话一行、每条消息一行，按用户查询、分页、删除。界面只读这层。聊天产品（含本仓库对照过的画布生成历史）都是这样做的：列表和成品在 PostgreSQL，Redis 只缓存查询。
2. **图的执行状态**继续放 checkpointer。它保存节点中间态，方便同线程接着跑。它不作为用户看得见的历史的唯一副本。

只把 checkpointer 从 Redis 换成 Postgres，解决不了换浏览器后的列表，还会把每一步的内部快照写进库，并且这些表不属于 Prisma 迁移。界面要的来源卡片、情绪、求助卡片也不该绑在 LangGraph 的 blob 格式上。

## 3. 选定方案

PostgreSQL 保存已完成轮次，作为界面和换端恢复的依据。Redis checkpoint 继续负责当前图的热状态。Redis 空了，下一轮从 PostgreSQL 把最近 30 轮灌回图的输入。

不采用：

- 只给 Redis 开 AOF。能抗重启，不能抗清空，也没有会话列表。
- 把 `RedisSaver` 换成 `PostgresSaver` 并直接拿 checkpoint 当历史。
- 给会话列表加数秒过期的 Redis 缓存。列表不在生成过程中连着变。

## 4. 数据模型

表由 Prisma 创建，与现有 `tenants` / `users` 一起迁移。写入发生在 FastAPI，对话结束的地方；FastAPI 用参数化 SQL 写这两张表，列名与 Prisma 保持一致。

`ChatSession`，映射表名 `chat_sessions`：

| 列 | 含义 |
| --- | --- |
| `id` | 会话编号，等于现有 `thread_id`（UUID 字符串），主键 |
| `tenantId` | 学校 id，外键 `tenants.id`，删除学校时级联 |
| `userId` | 用户 id，外键 `users.id`，删除用户时级联 |
| `title` | 列表标题。取第一条用户消息去空白后的前 40 个字；空则「新的对话」 |
| `createdAt` / `updatedAt` | 创建时间；每成功一轮更新 `updatedAt`，列表按它倒序 |
| `summary` | 旧轮次的滚动摘要，默认空字符串，见第 8 节 |
| `summarizedSeq` | 已被摘要覆盖到的最大 `seq`，默认 0，见第 8 节 |

索引：`(tenantId, userId, updatedAt DESC)`。列表查询不选 `summary`，它只在组装提示词时读。

`ChatMessage`，映射表名 `chat_messages`：

| 列 | 含义 |
| --- | --- |
| `id` | 主键，`cuid` 或 UUID |
| `sessionId` | 外键 `chat_sessions.id`，删除会话时级联 |
| `seq` | 会话内从 1 递增的序号。唯一约束 `(sessionId, seq)` |
| `role` | `user` 或 `assistant` |
| `content` | 正文 |
| `context` | 助手消息附带的资料上下文，可空字符串 |
| `sources` | JSON，来源卡片，默认 `[]` |
| `emotion` | JSON，可空 |
| `safety` | JSON，可空 |
| `createdAt` | 写入时间 |

一轮成功等于连续两条：用户消息 `seq = 2k-1`，助手消息 `seq = 2k`。

保留策略：产品记录**不**按 30 轮截断。30 轮只约束灌回给图的热状态，10 轮只约束发给模型的上下文。界面打开会话时返回该会话的全部已落库消息。单条 `content` 沿用现有接口，不另设字数上限；若以后要封顶，另开规格。

## 5. 写入时序

只在**一整轮图运行成功结束**后写库。流式过程中不写。出错、用户中止、图抛错，这一轮不出现在历史里。当时屏幕上已经打出来的半截回答刷新后消失，这与现在 Redis 未完成快照的表现一致。

成功的定义：`graph.stream` 正常结束，且事件流里没有 `error`。此时 Redis 里该线程的最新 `messages` 已经包含本轮 user 与 assistant（含 `finalize_node` 补上的 `emotion` / `safety`）。

写入在一个数据库事务里：

1. 按 `(id = thread_id, tenantId, userId)` 插入或更新 `chat_sessions`。已有标题且不是「新的对话」时不改标题。`updatedAt` 设为现在。
2. 取该会话当前最大 `seq`。若最后两条已经与本轮 user/assistant 的 `content` 完全相同，视为重复提交，不再插入。
3. 否则追加这两条，`seq` 连续。

第 2 步用来挡住同一次成功路径被调用两次。用户故意再发同一句话，会成为新的一轮，因为中间已经有更新的序号，最后两条不再等于这次要写的内容。实现时以「本轮在这次请求里只提交一次」为主，内容比对是额外保险。

访客（`GUEST`）不写这两张表，历史仍只在 Redis，并且不进入列表。

长期记忆的写入逻辑不动，仍在情感节点里。

## 6. 读取与 Redis 丢失后的恢复

`GET /api/sessions/{tid}/messages` 改为：

1. 用令牌里的学校和用户核对会话。没有属于此人的行时，不返回别人的数据。
2. 若 PostgreSQL 有消息，按 `seq` 升序返回。响应字段保持现在的 `role`、`content`、`context`、`sources`、`emotion`、`safety`。
3. 若这个编号从未落库、也没有删除标记，且 Redis 快照里有消息：把这些消息按上面的事务补写进 PostgreSQL，再返回。这只用于上线前已有、还没进库的对话。
4. 若存在删除标记：返回 404，不用 Redis 把正文补回来。
5. 两处都没有、也没有删除标记：返回 `[]`。

下一轮提问，在调用图之前：

1. 用现有的 `scoped_thread_id` 读 Redis 快照。
2. 快照里已有 `messages`：不要在输入里再带 `messages`。当前 state 的 `messages` 是整表替换，输入里再带会盖掉热状态。
3. 快照缺失或 `messages` 为空：从 PostgreSQL 取最近 30 轮（60 条）放进这一次的输入 state。图没有 checkpoint 时，输入就是初始 state。模型侧仍只使用最近 10 轮。

这样 Redis 清空后：列表还在，点进去正文还在，接着问时模型仍看得到最近 10 轮。

进行中的那一轮如果恰好处在 Redis 里、还没成功落库，会丢掉。规格接受这一点。要保住它，就得在流式开始前写用户消息、结束再写助手消息，失败时会出现「有问无答」的行。本规格选择不把未完成轮次展示出来。

## 7. 隔离

隔离分四层，前三层现在已经有，这一期只是把它们覆盖到新表；第四层是新增的。

**身份层。** JWT 里 `sub` 是用户 id，`tid` 是学校 id，由 Next 用 `AUTH_JWT_SECRET` 签，FastAPI 用 PyJWT 验，强制要求 `exp`、`iss`、`sub`。令牌 12 小时过期，访客 2 小时。换浏览器重新登录拿到的是同一个 `sub` 和 `tid`，所以下面所有查询都落到同一批行上——这就是「任意浏览器登录历史还在」成立的原因：历史认人，不认浏览器。

**线程层。** `scoped_thread_id(user, thread_id)` 把浏览器生成的编号收进 `{学校id}:{用户id}:{编号}`。编号本身是 UUID、由浏览器生成、会出现在地址栏里，所以必须假设它会泄漏。加前缀之后，别人拿到这个编号去读 Redis，命中的是他自己命名空间下的空线程，读不到正文。这一层保持不动。

**数据层。** 新加的两张表不依赖线程层的前缀，必须自己带条件：

- `chat_sessions` 的每一次读、写、删都带 `tenantId = 令牌.tid AND userId = 令牌.sub`，不能只按主键 `id` 查。
- `chat_messages` 只通过已经过滤过的 `sessionId` 访问，不提供按 `id` 直取。
- 行不存在、或存在但不属于这个人，一律 404，不用 403 或 200 区分。否则对方可以靠状态码把编号枚举出来。
- 同一个人在两所学校各有账号时是两个 `userId`，列表天然不串。

**浏览器层（新增）。** 现在退出登录只清令牌和用户资料，`zhiyue.threadId` 和地址栏的 `?tid=` 会留下来。同一台机器接着登另一个账号时，前端会带着上一个人的编号去拉消息，服务端会按数据层返回 404——不泄漏，但界面上会出现一次莫名其妙的空会话。第 10 节要求退出登录时一并清掉这两处。

不在本规格内：教务凭证 `jw:cred:{学校}:{用户}` 和长期记忆 `memory:{学校}:{用户}` 已经各自带学校和用户前缀，隔离方式不变。

## 8. 上下文压缩

### 8.1 现在的行为

每一轮都把最近 `MAX_PROMPT_TURNS`（默认 10）轮原文整段塞进提示词，三条路径都一样：闲聊在 `graph_app.py` 的 `_generate`，陪伴在 `_comfort_answer`，工具问答在 `_agent_answer` 里作为 `agent.run` 的 `history`。超出 10 轮的内容直接不进提示词。

两个后果。一是**话题断层**：第 11 轮之后，前面说过的专业、年级、正在办的事全部消失，用户感觉助手突然失忆，而历史明明还在库里。二是**长度不可控**：10 轮是固定轮数，不是固定长度。工具问答一轮的回答可能是 40 行空教室表格，10 轮这样的回答就是上万字，而闲聊 10 轮可能只有几百字。同一个数字同时管这两种情况，要么浪费要么溢出。

### 8.2 方案：滚动摘要 + 字符预算

做法是业界通行的 running summary：把滑出窗口的旧轮次压成一段摘要，摘要随会话一起存库，每轮注入一次。

`chat_sessions` 增加两列：

| 列 | 含义 |
| --- | --- |
| `summary` | 旧轮次的摘要正文，默认空字符串，上限 800 字 |
| `summarizedSeq` | 已被摘要覆盖到的最大 `seq`，默认 0 |

**生成**在一轮成功落库之后、在后台进行，不占用这一轮的响应时间。触发条件：`最大seq - summarizedSeq > 2 × KEEP_TURNS`。把 `(summarizedSeq, 最大seq - 2×KEEP_TURNS]` 区间内的消息连同现有 `summary` 一起交给模型，产出新的 `summary`，并把 `summarizedSeq` 推到这个区间的末尾。整个过程失败就什么都不改，下一轮再试——这一点和第 15.3 节「记忆或落库失败不打断已经生成的回答」是同一个原则。

摘要提示词只保留稳定事实：学生的身份信息（专业、年级、校区）、正在办的事、已经给过的结论和链接、明确表达过的偏好。寒暄、情绪、一次性措辞一律丢掉。这条规则抄自第 15.2 节 Shinsekai 的抽取规则，区别是它抽的是跨会话长期记忆，这里抽的是会话内上下文。

**注入**时提示词变成：系统提示 + （`summary` 非空时）一条标明「这是本次对话更早的内容摘要」的系统消息 + 最近若干轮原文 + 当前问题。三条路径共用同一个组装函数。

**最近若干轮**从固定 10 轮改成**字符预算**：从最新一轮往回取，累计字符超过 `MAX_PROMPT_CHARS`（默认 6000）就停，但至少保留 2 轮，至多仍不超过 10 轮。这样 40 行表格那种长回答不会把窗口撑爆，纯闲聊也不会白白只给 10 轮。

### 8.3 不动的部分

- 库里的正文不压缩。第 4 节的保留策略不变，界面打开会话仍然看到全部原文。压缩只作用于发给模型的内容。
- Redis 热状态仍按 `MAX_STORED_TURNS`（30）截断，这一层不变。
- 摘要**不是**长期记忆。摘要属于一个会话，随会话删除而删除；`memory:{学校}:{用户}` 跨会话，仍按现状由情感节点维护。两者互不替代。
- `agent.run` 内部那一轮的 tool 消息不进摘要，也不进历史。工具结果已经有 `TOOL_RESULT_CHARS`（6000）截断。

### 8.4 退化行为

`summary` 为空、或摘要节点从未成功过时，行为与现在完全一致：只有最近若干轮原文。所以这一节可以单独关掉（把触发阈值设为无穷大），不影响第 1 到 7 节。

## 9. 接口

均须登录。访客调用列表返回空数组；调用某条会话的消息、删除，返回 404。成员只能看见 `tenantId` 与 `userId` 都匹配的行。不匹配或编号不存在，统一 404，避免用状态码分辨编号是否属于别人。

`GET /api/sessions`

查询参数 `limit`，默认 50，最大 100。按 `updatedAt` 倒序。

```json
[
  {
    "thread_id": "8214afc4-7b79-4452-b95a-8102171ed163",
    "title": "图书馆周末开门吗",
    "updated_at": "2026-10-15T01:36:00Z"
  }
]
```

`POST /api/sessions`  
行为不变：只签发 UUID，不插行。没有发出去并成功完成的对话不进列表。

`GET /api/sessions/{thread_id}/messages`  
见第 6 节。

`DELETE /api/sessions/{thread_id}`  
删除该用户的会话行（消息级联删除），并写入删除标记 `(tenantId, userId, threadId)`。Redis 里的 checkpoint 能删则删。删不掉时，删除标记仍阻止第 6 节用这份快照把会话补回来。之后向该编号再发 `POST /api/chat` 也返回 404，不新建行。响应 `204`。

`POST /api/chat`  
请求体不变。成功结束后按第 5 节落库。落库失败记日志，不把已经生成并推给前端的回答改成失败；下次打开这条会话时若库中缺这轮、Redis 仍在，第 6 节第 3 步会补上。若当时 Redis 也没了，这一轮无法恢复。

## 10. 前端

主界面增加会话列表，数据来自 `GET /api/sessions`。点一项：把该 `thread_id` 写入地址栏和 `zhiyue.threadId`，再拉消息。这与现在 `useChat` 恢复单个 `tid` 的方式相同。

打开页面时：

- 地址栏或 `localStorage` 里有 `tid`：继续打开它，并同时拉列表。
- 都没有：拉列表。列表非空则打开最近一条；列表为空则保持现在的逻辑，向 `POST /api/sessions` 要一个新编号。

「新对话」仍调用 `POST /api/sessions` 并清空屏幕。在第一条消息成功之前，列表里不出现这项。

退出登录时，除了清除令牌和用户资料，还要删掉 `zhiyue.threadId` 并去掉地址栏上的 `tid`。否则同一浏览器接着登另一个账号时，还会带着上一个人的编号。

嵌入挂件不改：仍只用 `sessionStorage`，不请求会话列表。

## 11. 上线与旧数据

1. Prisma 迁移添加两张表。
2. 部署后不批量扫 Redis。旧对话在用户再次打开那个 `tid` 时按第 6 节回填。
3. 换了浏览器、本地又没有旧 `tid` 的用户，看不到迁移前的对话。那些编号只存在旧浏览器里。这是本规格上线前的存量缺口，不做全库扫描就无法补。审查时若要保留存量，需要另定一次离线任务：从 Redis 的 checkpoint 键解析 `学校:用户:tid` 并回填。默认不做。

## 12. 测试

- 用户 A 的列表不含用户 B、也不含另一所学校的同一个人。
- 一轮成功后，库中有会话行和按 `seq` 排列的两条消息；标题来自第一条用户消息。
- 图返回错误或客户端中止后，库中条数不变。
- 清空该线程的 Redis 后，`GET messages` 仍返回已落库正文；再提一个问题，送进模型的历史含此前轮次。
- Redis 有消息、库中没有、且没有删除标记时，第一次 `GET messages` 会回填，第二次不再重复插入。
- 删除后再用同一编号取消息或继续聊天，得到 404；即便 Redis 快照还在，也不会重新出现在列表里。
- 同一轮成功回调执行两次，消息不重复。
- 访客聊天不产生 `chat_sessions` 行。
- 删除后列表消失，原编号再取消息或继续聊天得到 404。

隔离（第 7 节）：

- 直接拿别人的 `thread_id` 调 `GET messages`、`DELETE`，都得到 404，而不是 403 或 200。
- 同一台机器上 A 退出、B 登录后，前端不再带着 A 的 `tid` 去请求。
- 同一个人在两所学校各有账号时，两边的列表互不出现对方的会话。

上下文压缩（第 8 节）：

- 轮次累计超过阈值后，`summary` 非空且 `summarizedSeq` 单调增；再跑一次不重复摘要同一区间。
- 摘要调用抛错时，这一轮回答正常返回，`summary` 和 `summarizedSeq` 都不变。
- 提示词里最近若干轮的总字符数不超过 `MAX_PROMPT_CHARS`，且至少有 2 轮。
- 单轮回答极长（如 40 行表格）时，窗口自动缩到 2 轮，不再固定 10 轮。
- `summary` 为空时，组装出的提示词与现在逐字一致。
- 删除会话后，它的 `summary` 一起消失，不影响同一用户的其他会话。

## 13. 非目标

- 不把「记住」的长期记忆迁到 PostgreSQL。
- 不替换 `RedisSaver`，不为会话列表加缓存。
- 不保存生成过程中的半截回答。
- 不提供跨会话搜索。
- 不改 JWT 的有效期和签发方式。
- 不加密库里的对话正文。正文已经按学校和用户隔离，再加一层应用层加密会让运维和排查都没法看，另案讨论。
- 不把摘要做成向量检索。第 8 节只做线性的滚动摘要，不引入句向量。

## 14. 请审查的决定

1. 未完成的一轮不入库。接受刷新后半截回答消失。
2. 库中保留完整正文，不只留 30 轮。30 轮仅用于灌回图，10 轮仅用于模型。
3. 上线前只存在 Redis、且用户换过浏览器的旧对话，默认不回填。
4. 删除会话放进这一期，并用删除标记阻止 Redis 快照把已删会话补回来。
5. 长期记忆仍保持现状。第 15 节里标成「可后续适配」的条目不进入这一期。
6. 滚动摘要（第 8 节）和落库（第 3 到 7 节）要不要同一期上。摘要依赖 `chat_messages` 已经在写，所以顺序上必须在后；但可以拆成两次发布，先把历史存下来，再加压缩。
7. 摘要用哪个模型。用本校配的对话模型最省事，但它可能是贵的那个；也可以固定走平台的便宜模型。摘要质量要求不高，倾向后者。
8. 最近窗口从「10 轮」改成「6000 字符、至少 2 轮至多 10 轮」。这会改变现有所有会话送进模型的内容，是一次行为变更，需要确认。
9. 消息行要不要加一列 `tables`（结构化表格），见《工具准确性与表格呈现》规格第 3 节。加了之后刷新页面空教室表格还在，不加就只能靠模型重新排版。

## 15. 对照 Shinsekai 的记忆管理

来源：[RachelForster/Shinsekai](https://github.com/RachelForster/Shinsekai) `main`，提交 `f77090122f66ca7644c13bfa97fb7b44a21fb0fe`。它是本地桌面 Galgame，不是多租户 Web。记忆分成两套，都不进 Redis。

### 15.1 会话正文

目录在本地磁盘。一个会话一个目录：`active.json` 是当前分支正在用的消息，`branches.json` 是分支树。进程中断后，先读 `active.json`（含未替换完成的临时文件）；它有内容时以它为准，不用旧的分支文件覆盖。清空之后留下的空 `active.json` 表示「用户删过」，不能再用分支文件把历史救回来。

这和本规格的拆法相同：PostgreSQL 的消息行对应 `active.json`，Redis checkpoint 对应可以丢掉的热状态。分支树是剧情分叉，校园助手没有这层，不引入。

由此收紧第 6、9 节：库是空的，有两种意思。一种是这条对话还没迁进库，可以从 Redis 补一次。另一种是用户已经删除，必须有删除标记，禁止补回。

### 15.2 跨会话长期记忆

实现在 `ai/memory/`，用 [mem0](https://github.com/mem0ai/mem0)。向量放在本机 Qdrant（`data/memory/qdrant`，`on_disk=True`），变更历史放在 `data/memory/mem0_history.db`。向量模型是本地的 `paraphrase-multilingual-MiniLM-L12-v2`（384 维）。归属键是角色名，mem0 的 `user_id` 用这个名字。

使用方式：

- 每轮用户发言前，按这句话做语义检索，默认取 5 条，写成一条系统消息插进上下文。同一轮不重复插入。检索失败或记忆服务还在加载时，这轮照常回答。
- 不在每条消息上抽记忆。助手每回复满 5 个用户回合，才把最近 16 条对话交给模型抽取。抽取与回复分开，在后台线程里做。退出时再把缓冲区里还没抽的部分补抽一次。
- 抽取提示词只留稳定事实、偏好、关系、承诺、目标和人设状态。临时情绪、废话、一次性措辞丢掉。每个片段最多 8 条，每条最多 800 字。
- 写入前先查重：文本规范化后相同，或与已有条目的相似度达到 0.92，就不再插入。`mem.add(..., infer=False)`，避免 mem0 再抽一次。
- 向量库还没就绪时，待写条目先放进 `data/memory/pending_queue.json`（先写临时文件再替换）。进程重启后队列还在，就绪后再刷进向量库。

校园项目里对应的是 Redis 哈希 `memory:{学校}:{用户}`：按字面重合挑条目，上限 80 条、每条 200 字，情感分析同一次调用里顺带抽取，「记住：」立即写入。它不按语义检索，也没有独立的写入队列。

### 15.3 这一期采纳

- 正文与热状态分开。已写在第 3 节。
- 删除是明确状态，热缓存不能把已删内容救回。已写进第 6、9 节。
- 记忆或落库失败不打断已经生成的回答。第 9 节对 PostgreSQL 写入失败已是这个态度；Shinsekai 对长期记忆检索失败同样如此。

### 15.4 不采纳

- 不引入 mem0、本机 Qdrant，也不在服务器上下载句向量模型。那是单机桌面的做法，和现有 PostgreSQL 加 Redis 的部署不符。
- 不做会话分支、分叉存档。
- 不把长期记忆的归属从「学校 + 用户」改成角色名。

### 15.5 可后续适配，不在这一期

这些只作为下一份长期记忆规格的候选，不改变第 13 节「这一期不迁长期记忆」。

- 抽取与回答脱钩：每 N 轮（他们默认 5）用最近若干条对话在后台抽取，而不是堵在情感分析那一次调用里。
- 抽取规则写明只保留稳定事实，不保留临时情绪。
- 检索改为按问题的语义取少数几条再注入；注入文本标明是背景，且同一轮只注入一次。在此之前，现有的字面重合检索继续用。
- 写入前除了现有的全文相同去重，可再加相似度阈值（他们用 0.92）。没有向量之前做不到语义去重。
- 向量库或 Redis 暂时不可用时，用一张持久队列保住待写记忆，而不是直接丢掉。会话正文这一期用「Redis 还在就回填」覆盖，不另做队列。
